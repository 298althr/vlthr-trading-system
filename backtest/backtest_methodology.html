Overview & Objectives

Mission Context

The user observed a losing streak in live paper trading — pattern of 5 losses, 1 win, 5 losses — that diverged significantly from backtest expectations (56.4% win rate, PF 1.56). The mission was to audit the entire pipeline, build a faithful backtest simulation, validate it against live behavior, stress-test under real-world conditions, and document every step with full transparency.

This document captures the complete methodology from initial audit through staged stress testing and performance optimization — over 24+ hours of iterative development.

Data Opportunity
  • Local Parquet OHLCV from Bybit
  • 5 active symbols + 1 disabled
  • 15m execution + 4h context TF
  • ~17,000 bars per symbol (6 months)
  • Enriched: OI, funding, L/S ratio
Strategy Opportunity
  • Trend following + mean reversion
  • Per-symbol strategy assignment
  • DQS-weighted adaptive scoring
  • Kelly-band position sizing
  • Regime-aware SL/TP scaling
Backtest Method
  • Bar-by-bar replay (no look-ahead)
  • Control vs Treatment A/B
  • 5-stage stress testing
  • Deterministic seeded simulation
  • 15 runs in 12 min 26 sec

Development Timeline

Phase 0 — Live Audit & Problem Discovery

Audited full system architecture, verified all parameters in portfolio_config.py against live trade outcomes. Found max_trade_hours mismatch: ETHUSDT was 12h in backtest but 24h in live; BNBUSDT was 12h but 48h in live. Generated 8 hypotheses for live/backtest divergence.

Phase 1 — Backtest Framework & Control Run

Built standalone bar-by-bar backtest engine. Ran control mode over Jan–Jun 2026. Result: 1,441 closed trades, 56.4% win rate, PF 1.56, +$8,476.84 PnL, all 6 gates PASS. Tested Kelly=0.25 for DQS≥85 — degraded all metrics, validated V7 veto.

Phase 2 — Treatment A/B & Decoupled Architecture

Moved V7 veto from scanner to risk gate (Treatment A). Added crowding detection, data quality scoring, intent-vs-outcome logging (Treatment B). Control and Treatment A identical; Treatment B within 0.3%.

Staged Stress Testing

5 stages × 3 modes = 15 runs. Baseline, latency (15min delay), data gaps (5%), downtime (2h/7days), combined. Key finding: latency is the most damaging stressor. PF drops 3.10→2.46, win rate -4.2pp.

Performance Optimization

Initial stress test took 3+ hours. Fixed: cached daily bias (757s→0s), O(1) bar lookups, binary search for enriched slices, scan result caching. Final: 12 min 26 sec for 15 runs.

Data Quality States

The backtest computes a 0–100 data quality score for each signal (Treatment B only). Score = freshness × 0.40 + completeness × 0.40 + outliers × 0.20

Freshness (40%)

How recent is the last bar vs scan timestamp. Score = max(0, 100 - (staleness_min / 15 × 100)). 15min stale = 0; current = 100.

Completeness (40%)

Gap count in last 96 bars (1 day). Gaps > 20min count. Score = max(0, 100 - gap_count × 5).

Outliers (20%)

Bars where |z-score| > 5σ in last 96 bars. Score = max(0, 100 - outlier_count × 10).

DQS Scoring Methodology

The Dynamic Quality Score (DQS) is the core signal confidence metric, computed by score_signal_adaptive() in adaptive_scorer.py.

Architecture: Weighted-Max with Multipliers

DQS = (tech_raw × 0.40 + struct_raw × 0.30 + ctx_raw × 0.30
       + pullback_bonus + liquidity_bonus)
      × combined_mult - contra_penalty - regime_penalty

Clamped to [0, 100]. Additional hard caps applied post-computation.

Why weighted-max instead of pure weighted average? A pure average allows a strong context domain to mask a failed technical domain. The weighted-max ensures any single strong domain can carry the signal, but the weighted average base ensures a failed technical drags the score down.

V2 Strategy Filters

Applied after DQS scoring but before risk gate. Can reject signals, change strategy, or scale TP.

Filter 1: Daily Bias ▶

Input: load_daily_bias(symbol) → {bias, rsi}

  • Trend-following LONG + bias BEAR → REJECT
  • Trend-following SHORT + bias BULL → REJECT
  • MR SHORT + bias BULL + RSI<70 → REJECT
  • MR LONG + bias BEAR + RSI>30 → REJECT
1
Daily bias acts as a regime filter. We don't want trend signals fighting the daily trend. For MR, we allow counter-trend but only at RSI extremes.
Filter 2: Volume + RSI Momentum ▶

Volume ratio: < 0.15 → REJECT (no liquidity)

RSI momentum: LONG + RSI change < -5 → REJECT; SHORT + RSI change > +5 → REJECT

Filter 3: Dynamic Strategy by Regime ▶

Trending → force trend_following; Ranging → force mean_reversion; Volatile → keep original.

1
Market regime should dictate strategy, not the symbol's default. Volatile is ambiguous — neither strategy has clear edge, so we don't override.
Filter 4: TP Scaling by ATR Percentile ▶

ATR percentile >70% → TP×1.3; <30% → TP×0.8; else TP×1.0

Filter 5: BTC Correlation (XRP only) ▶

XRP LONG + BTC momentum <-2.5% → REJECT; XRP SHORT + BTC momentum >+2.5% → REJECT

1
XRP is highly BTC-correlated. ±2.5% threshold chosen as meaningful momentum — anything less is noise. Only applies to XRP because other symbols have stronger fundamentals.
Caching

load_daily_bias() cached in _daily_bias_cache — eliminated 757s redundant disk I/O across 15 stress test runs.

Why max 8 active? All 5 crypto symbols are correlated. 8 concurrent positions in a correlated cluster = betting on same direction 8 times. Raised from 5 for faster cycling.

Simulation Logic

Latency

Signals delayed by latency_bars. Signal at bar N acted on at bar N+latency. Worse fills, more expirations, DQS may change.

Data Gaps

Each bar, each symbol: rng.random() < gap_prob → gapped. Scanning + repricing skipped. Exits STILL RUN (exchange-side).

Downtime

2h outage every 7 days at 8am UTC. Scanning + pending skipped. Exits STILL RUN. Delayed signals tick down but don't process.

Critical Design Decision

Exits ALWAYS run, even during gaps/downtime. Exchange SL/TP orders execute independently of our server. Skipping exits would undercount SL hits and overcount TP hits.

1
Why 5 stages? Each isolates one stressor to identify which causes most degradation. Combined alone wouldn't reveal latency as primary risk.
2
Why seed=42? Fixed seed ensures same bars gapped across all 3 modes. Any difference is due to mode logic, not RNG variance — critical for fair comparison.
3
Why 2h/7days downtime? Realistic server restart. 26×2h=52h=0.4% of time. 8am UTC = low-liquidity maintenance window.

Key Findings & Explanations

Finding 1: Latency is the Most Damaging Stressor

Data: 1-bar (15min) delay alone drops PF 3.10→2.46 (-20.6%), win rate -4.2pp, final balance -$2,663 (-13.0%). SL hit rate jumps 63.5%→67.9%.

Why: Delayed entries mean worse fill prices. Price moved 15min — if against us, SL is closer; if favorable, TP is closer. 3.1% expired rate (vs 1.4% baseline) shows signals expiring during delay.

Parameter moving forward: Reduce pipeline cadence from 15min to 5min for signal scanning. Would reduce latency window from 15min to 5min, potentially recovering ~60% of lost edge.

Finding 2: Data Gaps Alone Slightly Improve Performance

Data: 5% gap rate → PF 3.23 (+4.2%), win rate 36.9% (+0.8pp), final balance $20,917 (+$385 vs baseline).

Why: 5% random gap rate acts as accidental noise filtering. Marginal signals skipped because scan bar is gapped. Remaining signals slightly higher quality. Trade count only drops 0.9%.

Parameter moving forward: No action needed — data gaps at 5% are benign. At 10% (combined), effect reverses because too many signals missed.

Finding 3: Downtime Has Moderate Impact

Data: 26 two-hour outages → PF 2.96 (-4.5%), trades -0.8%, final balance $20,162 (-$370 vs baseline).

Why: Downtime only affects scanning and repricing — exits still execute. 52 hours = 0.4% of total time. Impact limited because outage windows fall during low-activity periods.

Parameter moving forward: Current downtime tolerance acceptable. Consider moving maintenance to weekends or Asian session.

Finding 4: Combined Stress is Dominated by Latency

Data: Combined PF = 2.46, matching latency-only PF = 2.46. Combined trades = 1,370 vs latency-only 1,444 (-5.1%). The additional trade reduction comes from 10% data gaps + downtime.

Why: Latency is the dominant factor because it affects every signal. Data gaps (10%) and downtime (0.4%) are probabilistic — they only affect some bars. The PF degradation is entirely from latency; the trade count reduction is from all three combined.

Parameter moving forward: Prioritize latency reduction. If we can get latency to 0 (real-time processing), combined stress PF would recover to ~2.96 (downtime-only level).

Anti-Hallucination Rules

Documentation Rules
  1. Ground in code: Every parameter value must be traceable to portfolio_config.py, calibration.json, or backtest_runner.py.
  2. Ground in data: Every result must be sourced from actual CSV output files (stress_test_staged_results.csv, stress_test_results.csv, etc.).
  3. No speculation: If a result is not in the data, state "not available" — do not estimate or extrapolate.
  4. Cite sources: Each section references the source file for its data.
  5. Deterministic verification: All runs use seed=42. Re-running should produce identical results.
Backtest Execution Rules
  1. No look-ahead: All data merges use merge_asof(direction="backward"). No future data is used.
  2. Bar-by-bar replay: Each timestamp processed in order. State updated sequentially.
  3. Seeded RNG: random.seed(42) for data gaps and downtime generation.
  4. Exit order matches live: TIME_EXIT → SL_HIT → TP_HIT (conservative).
  5. Dynamic SL matches live: Ported from computeDynamicSL in server.cjs.
  6. Fees included: TAKER_FEE=0.00055 applied to entry and exit.

Known Divergences

The three ⚠ items above are the primary sources of live/backtest divergence. Live trading experiences real slippage and variable execution timing that the backtest cannot fully replicate. The order book data in backtest is approximated from OHLCV rather than real OB snapshots, which may affect the structure domain scoring.

How to Validate Results

  1. Check all 6 validation gates pass (win rate, PF, expectancy, DD, expired rate, TP hit rate)
  2. Verify deterministic: re-run with same seed, compare CSV outputs byte-for-byte
  3. Compare live trade outcomes to backtest signals at same timestamps
  4. Monitor for divergence: if live WR < 40% while backtest WR > 50%, investigate execution differences
  5. Re-calibrate when closed trade count reaches 100+ samples
