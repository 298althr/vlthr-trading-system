FEROS Backtest Upgrade Plan

Feature Engineering Research Operating System · Anti-Overfit Backtest Architecture
v1.0 · 2026-07-16

Overview

This plan upgrades the VLTHR backtest from a single-path bar replay into a FEROS-driven research operating system. The goal is to eliminate overfitting by adding walk-forward optimization, multi-dimensional validation, feature registries, regime-aware testing, and out-of-sample verification before any parameter touches the live pipeline.

What FEROS Changes

The current backtest is a single-pass bar replay with fixed parameters. FEROS converts it into a stateful research system where every feature, indicator, experiment, and calibration is tracked, versioned, and validated across multiple independent dimensions before it reaches production.

The live trading engine only consumes validated calibration JSON. FEROS sits between raw data and the live engine as a research gate.

Core Anti-Overfit Principles

  • Walk-forward optimization. Parameters are optimized on a rolling window and tested on the next unseen window. No parameter touches the test set before it is frozen.
  • Feature registry with SHAP importance. Every feature is tracked with prediction accuracy, confidence, and lifecycle state. Features that drift are deprecated, not silently kept.
  • Multi-dimensional validation. No single metric validates a feature. Mathematical, statistical, behavioral, and performance validation must converge.
  • Regime-aware testing. Features and parameters are tested per regime (trending, ranging, volatile, etc.). A feature that works only in one regime is labeled as such, not deployed globally.
  • Out-of-sample and stress validation. Every parameter set is tested on data it has never seen, under stress conditions (latency, gaps, downtime), before approval.
  • Production shadow mode. New calibrations run in shadow against live data before activation. Discrepancies are logged.
  • Self-learning loop. After every pipeline run, the system identifies what knowledge was created, which assumptions failed, and which experiments to run next.

Build Phases

1Data Lake Expansion

Goal: Ingest all 12 new data sources into the existing Parquet data lake.

  • Create ingestion scripts for economic calendar, Fear/Greed, BTC dominance, DXY, equities, news sentiment, on-chain metrics
  • Backfill aggtrade and liquidation data from Bybit
  • Store all data in Parquet with standard schema: timestamp, symbol, value, source, pipeline_id, hash
  • Verify data completeness and alignment with existing OHLCV timestamps

Protocol GBEGP Phase 0 (environment setup), STBP Section 6 (supply chain vetting for new API clients)

2Feature Engineering Pipeline

Goal: Build the feature registry and engineering pipeline.

  • Create SQLite/DuckDB feature registry with the FEROS schema (feature_id, formula, parameters, dependencies, density, validation_status, confidence, shap_importance, lifecycle_state)
  • Engineer features across all domains: price, volume, liquidity, OI, funding, session, regime, economic, intermarket, sentiment, on-chain, decision history
  • Compute density metrics for every feature: occurrence, activation, success, failure rates
  • Automatically discover and store feature dependencies as a DAG

Protocol CCP Section 3 (build one feature at a time, validate before next), RODP (one concern per file)

3Validation Framework

Goal: Implement multi-dimensional validation for every feature.

  • Mathematical validation: formula correctness on synthetic data, numerical stability, boundary testing
  • Statistical validation: distribution analysis, stationarity (ADF test), mutual information, autocorrelation, variance inflation
  • Behavioral validation: regime consistency, session consistency, cross-symbol consistency, market-cycle consistency
  • Performance validation: IC (information coefficient), Sharpe, Sortino, win rate contribution, PF contribution
  • Stress validation: latency, data gaps, downtime, slippage simulation
  • Production shadow: run feature against live data, compare with backtest expectations

Gate Feature approved only when all 6 validation layers pass with confidence > 0.8

Protocol PIVP (validation gate per feature), FEROS Decision Framework (no single metric approval)

4Walk-Forward Experiment Orchestrator

Goal: Replace single-pass backtest with walk-forward optimization.

  • Implement rolling window train/test split with 1-month purge gap
  • Integrate Optuna for Bayesian hyperparameter optimization on train windows
  • Implement purged k-fold cross-validation (combinatorial purged cross-validation from Lopez de Prado)
  • Regime-conditional testing: optimize and test parameters per regime separately
  • Monte Carlo simulation: reshuffle trade order 1000x to compute probability of ruin
  • Aggregate OOS results across all windows. Reject parameters with high variance across windows.

Protocol SMP Phase 0 (functional inventory of existing backtest before migration), DFDI (decision-first: validate hypothesis before running experiment)

5Calibration Registry and Export

Goal: Replace the broken flat-0.5000 calibration with a versioned, validated model.

  • Build calibration registry: each calibration versioned, linked to experiment and walk-forward window
  • Train calibration model on walk-forward OOS predictions (not in-sample)
  • Enforce minimum sample size (100+ per symbol, up from 5)
  • Export validated calibration as JSON for live pipeline consumption
  • Shadow mode: run new calibration alongside live, log discrepancies for 7 days before activation
  • Rollback mechanism: revert to previous calibration if drift detected

Protocol GBEGP Section 3 (dev to production promotion), STBP Section 4 (destructive op gate for calibration swap)

6Self-Learning Module

Goal: Close the loop. After every pipeline run, the system learns.

  • Build knowledge graph in networkx with persistence to SQLite
  • After each experiment: identify what knowledge was created, which assumptions failed, which dependencies changed
  • Drift detection: monitor feature performance over time, flag features with declining IC or confidence
  • Auto-generate experiment queue: based on failures and knowledge gaps, propose next experiments
  • Knowledge density metrics: track occurrence, activation, success rates per feature per regime

Protocol RODP Section 7 (progress reports), FEROS Self-Learning tab

7Live Integration and Shadow Deployment

Goal: Connect FEROS output to the live pipeline safely.

  • Docker container for FEROS with volume mounts for data and metadata
  • Live pipeline reads calibration JSON from FEROS export directory
  • Shadow mode: FEROS runs alongside live pipeline, comparing signal quality
  • 7-day shadow burn-in before any calibration goes live
  • Automated rollback if live performance deviates from shadow expectations by more than 2 sigma
  • Dashboard: FEROS status, experiment queue, feature health, calibration version

Protocol GBEGP Section 3 (promotion), STBP Section 5 (prod posture), PIVP (exit gate before promotion)

Validation Architecture

No single metric validates a feature or parameter set. Evidence must converge from multiple independent sources.

1. Mathematical Validation

  • Formula correctness on synthetic data with known outputs
  • Numerical stability (no overflow, no division by zero)
  • Boundary testing (empty arrays, single values, NaN inputs)
  • Missing value handling (forward fill vs drop vs impute)
  • Precision and overflow checks
  • Unit consistency (percentages vs absolute vs basis points)

2. Statistical Validation

  • Distribution analysis (normal, fat-tailed, bimodal)
  • Stationarity test (Augmented Dickey-Fuller)
  • Mutual information with target variable
  • Correlation and autocorrelation (Ljung-Box)
  • Cointegration with other features (redundancy check)
  • Variance Inflation Factor (VIF < 5 required)
  • Noise-to-signal ratio

3. Behavioral Validation

  • Regime consistency (does feature behave same in trending vs ranging?)
  • Session consistency (London vs NY vs Asia)
  • Economic event consistency (pre/post FOMC, CPI)
  • Cross-symbol consistency (does feature work on BTC and SOL?)
  • Market-cycle consistency (bull vs bear vs sideways)

4. Performance Validation

  • Win rate, profit factor, expectancy contribution
  • Drawdown, Sharpe ratio, Sortino ratio
  • Recovery factor, MAR ratio
  • Information coefficient (IC) with forward returns
  • Capital efficiency, trade efficiency
  • Calibration accuracy (Brier score, log loss)
  • Signal stability (decay half-life)

5. Stress Validation

  • Latency simulation (1-bar, 2-bar, 3-bar delay)
  • Data gap simulation (5%, 10%, 20% missing bars)
  • Downtime simulation (2h, 4h, 8h outages)
  • Slippage modeling (realistic spread, gap risk on SL)
  • Fee sensitivity (2x, 3x current fee schedule)
  • Liquidation cascade simulation

6. Production Shadow Validation

  • Run new calibration alongside live for 7 days
  • Compare signal quality: DQS distribution, win rate, PF
  • Log every discrepancy between shadow and live
  • Drift detection: PSI (Population Stability Index) > 0.2 triggers alert
  • Rollback if shadow performance deviates > 2 sigma from backtest expectation
  • No calibration goes live without passing shadow burn-in

Approval Gate

A feature or parameter set is approved only when:

  • All 6 validation layers pass
  • Confidence score > 0.8 across all layers
  • Walk-forward OOS results are stable (variance < 20% across windows)
  • No single metric is used as the sole justification
  • Shadow mode burn-in completes without drift alert

FEROS Decision Framework Never approve features because they improve one metric. Approve features because they consistently improve the overall decision system.

Success Criteria

  • Walk-forward OOS win rate within 5pp of live win rate. If backtest says 35% and live delivers 30%, that is acceptable. If backtest says 36% and live delivers 13%, that is overfit.
  • Calibration gate produces non-trivial probabilities. No more flat 0.5000. Brier score < 0.25 on OOS data.
  • Feature registry tracks at least 50 validated features with SHAP importance, lifecycle state, and drift monitoring.
  • SL overshoot detected and modeled. Backtest slippage matches live observed slippage within 20%.
  • Shadow mode runs 7 days with < 2 sigma deviation from backtest expectations before any calibration goes live.
  • Self-learning loop generates at least 3 experiment proposals after the first full pipeline run.

Risks and Mitigations

RiskMitigation
Walk-forward reveals that current strategy has no edge OOS Accept the finding. Better to know now than keep losing live. Pivot to new feature sets identified by FEROS.
New data sources have gaps or API rate limits Backfill aggressively in Phase 1. Use free tiers with rate limiting. Cache everything to Parquet.
Feature engineering produces too many features (curse of dimensionality) VIF check eliminates redundant features. SHAP importance ranks by contribution. Cap at top 30-50 features by IC.
Calibration model overfits to walk-forward OOS predictions Use isotonic regression (low capacity). Enforce minimum 100 samples per symbol. Monitor Brier score on live shadow data.
SMP migration breaks existing backtest functionality Characterization tests on old backtest first. Incremental migration per SMP. Old backtest stays available until parity verified.
