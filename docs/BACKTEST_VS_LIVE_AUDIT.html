VLTHR Systems Audit

Why the backtest wins and the live test loses

This report checks the practice test (the backtest) against the real running system (live paper trading). It finds where the two do not match, explains each gap in plain words, and gives an exact plan to fix it. It also shows how to add one smart review step, run by an AI, to the practice test.

Made on July 13, 2026. Sources: backtest/backtest_phase2_results.csv, backtest/backtest_runner.py, the live Postgres database, pipeline/engine/portfolio_orchestrator.py, and backend/src/server.cjs. Every number here comes from those files. Nothing is made up.
The Short Version

What we found

The practice test says the system makes money. The real system is losing money. The gap is not bad luck. It is caused by a few clear differences between how the practice test pretends trades happen and how trades really happen.

The single biggest reason: The practice test is too kind about when a trade wins. On a 15 minute price bar that touches both the profit target and the stop loss, the practice test always books it as a win. The real system, which watches price all the time, books most of those as a loss. This one choice turns a winning practice test into a losing real system.

On top of that, the practice test was scored on the same six months of data that its settings were built from. That is like writing an exam after seeing the answer key. When the real system met a fresh month it had never seen (July), the edge fell apart. The practice test itself was already fading month by month, from a 60.7% win rate in January down to 52.3% in June. July continued that slide.

There are also real differences in the code. The live system moves the stop loss around while a trade is open. The practice test does not. The live system holds some coins far longer than the practice test allows. The live system has an extra safety check the practice test never runs. Each of these pushes the live result away from the practice result.

How the practice test decides a trade is done

The practice test walks forward one 15 minute price bar at a time. For each open trade it looks at the high and low of that one bar. The exact order of checks matters a lot, so here is the real code from backtest_runner.py:

if is_long:
    if trade.tp_price > 0 and high >= trade.tp_price:
        reason = "TP_HIT"      # profit target checked FIRST
    elif trade.sl_price > 0 and low <= trade.sl_price:
        reason = "SL_HIT"      # stop loss checked only if target missed

Read it closely. If a single 15 minute bar swings enough to touch both the profit target and the stop loss, the code always picks the profit target. It never asks which one happened first inside that bar. This is the "too kind" rule. It hands free wins to the practice test.

How Each One Works

The two pipelines, step by step

Both pipelines share the same brain for scoring signals. They differ in how a trade starts, how the stop is managed, and how a trade ends. Here they are as simple flowcharts.

The practice test (backtest)

1. Load history
Read past 15 minute price bars for all five coins.
↓
2. Score each coin
Give every coin a quality score from 0 to 100.
↓
3. Safety checks
Regime check, one trade per coin, daily limits, risk budget, block score 85 and up.
↓
4. Wait one bar, then start
Start the trade at the next bar close price. Almost always starts.
↓
5. Check exit each bar
Use the bar high and low. Check profit target first, stop loss second. Stop never moves.
↓
6. Write results to a file
Save every signal and every trade to the CSV.

The real system (live)

1. Pull fresh prices
Data service pulls new bars every 60 seconds.
↓
2. Score each coin
Same brain, every 15 minutes.
↓
3. Safety checks PLUS one more
Same checks, and an extra calibration check the practice test does not run.
↓
4. Set up, then confirm later
Create a pending trade. Next run may cancel it. 101 were cancelled this way.
↓
5. Watch price all the time
Check every 15 seconds using one live price. Stop loss is moved while open. Some coins held far longer.
↓
6. Save to database
Update the trade, the account, and the logs.
Where They Break Apart

The gaps, one by one

Each item below is a real difference found in the code and data. A red tag means a bug or unfair assumption. A yellow tag means a design gap where live and practice were built differently. A blue tag is context worth knowing.

Gap 1Bug / Unfair

The practice test hands free wins on wild bars

What happens: On a 15 minute bar that touches both the target and the stop, the practice test always calls it a win because it checks the target first. The real system, watching price all the time, will often hit the stop first and call it a loss.

Why it matters: This is the main reason the practice test shows 45% targets hit while live shows only 8.7%. It alone can turn a winning test into a losing system. Fix: in the practice test, when both are inside one bar, resolve using finer 1 minute data, or assume the worst case (stop first). Found in backtest_runner.py lines 541 to 554.

Gap 2Bug / Unfair

Scored on the same data used to build the settings

What happens: The coin settings, score weights, and thresholds were all tuned on Jan to Jun 2026, and then the practice test was scored on that very same Jan to Jun 2026. The tool has a "walk forward" option that trains on early data and tests on later unseen data, but the saved results did not use it.

Why it matters: The 56% win rate is a memory score, not a prediction score. The monthly slide from 60.7% to 52.3% shows the memory already wearing off. July, which the settings never saw, dropped to 24%. Fix: only trust results from data the settings never touched.

Gap 3Design Gap

The live system moves the stop loss, the practice test does not

What happens: The live code in server.cjs (function computeDynamicSL) moves the stop toward break even once a trade is 75% of the way to target, and tightens the stop every hour after hour 3. The practice test keeps the same stop for the whole trade.

Why it matters: In a choppy market, moving the stop closer means normal price noise stops the trade out before it can reach target. The practice test never suffers this. So live loses trades the practice test would have won. Fix: either add the same moving stop to the practice test, or turn the moving stop off live until it is proven in a fair test.

Gap 4Bug / Drift

Some coins are held much longer in live than in the practice test

What happens: The Python settings say every coin closes after 12 hours at most. The live backend uses its own list: Bitcoin 12 hours, Ethereum 24 hours, Solana 12 hours, XRP 12 hours, BNB 48 hours. So Ethereum and BNB run two to four times longer live than in the practice test.

Why it matters: Longer holding in a sideways market gives price more chances to hit the stop. The two systems are not testing the same rules. Fix: make one shared list of max hold hours and use it in both places. Found in server.cjs line 280 versus portfolio_config.py.

Gap 5Design Gap

Live has an extra safety check the practice test skips

What happens: Live Step 4 runs a calibration check that blocks a signal if its past success rate is too low. The practice test has no such check. Early on, the live check has too little history to work well, so weak signals slip through anyway.

Why it matters: The two systems approve different trades, so their results cannot line up. Fix: add the same calibration check to the practice test, and only turn it on live once it has enough history to help.

Gap 6Design Gap

Live cancels many trades before they start

What happens: Live sets up a trade, then waits for the next run to confirm it. Between those two moments the score can drop, a gate can fail, or the size can be too small, so the trade is cancelled. This happened 101 times, more than double the 46 that actually filled. The practice test almost always fills.

Why it matters: Live only trades a smaller and different set of signals. The trades that do survive may be the ones where price already moved against the plan. Fix: log why each one cancels, and make the fill rule the same in both systems.

Gap 7Design Gap

The live system keeps changing its own settings

What happens: Two functions, tune_tp_from_history and tune_regime_from_history, change the target and stop sizes based on recent closed trades. With only 46 trades, these change the rules based on a very small and unlucky sample. The practice test uses fixed settings.

Why it matters: The live rules drift away from the tested rules, so the practice test no longer describes the live system. Fix: freeze these auto changes until there are at least 100 closed live trades.

Gap 8Context

Neither system charges for slippage, and percent math differs

What happens: The live code stores a slippage number but does not subtract it from the trade result. The practice test ignores slippage too. Also, the two systems measure percent gain against different bases, so percent numbers cannot be compared directly.

Why it matters: Both are a little too optimistic on costs. This is small next to Gaps 1 to 4, but it should be fixed for a clean comparison. Fix: subtract a real slippage cost in both, and use the same percent base.

What To Blame Most

Root cause, ranked

Not every gap matters the same. Here is how much each one likely drives the loss, from most to least. Fix from the top down.

1
Too-kind exit rule in the practice test (Gap 1). This is why the target-hit rate is 45% on paper and 8.7% in real life. Biggest single driver.
2
Scored on its own training data (Gap 2). The 56% was never a real forecast. The monthly slide proves the edge was already fading.
3
Moving stop loss live only (Gap 3). In a choppy month this stops out good trades early. Present live, absent in the test.
4
Different max hold times (Gap 4). Ethereum and BNB run far longer live, adding stop-outs the test never sees.
5
Different gates and self-tuning (Gaps 5 to 7). These make the live system trade a different set of signals under different rules than the one that was tested.
The plain conclusion: The logic of the idea is not clearly broken. The problem is that the practice test was both too kind and graded on its own homework, while the live system quietly runs different rules. Close those gaps and the two will finally tell the same story. Only then can you trust either one.
Your Idea, Made Real

Adding one AI review step to the practice test

Yes, this is possible, and it is a good idea if you keep it in one place with a clear job. The AI should not trade. It should read the finished practice test, compare it to the live results, and write back a short, structured review. Think of it as a smart referee, not a player.

Where it goes in the pipeline

Put it right after the practice test finishes and the metrics are counted, and before any settings get changed. It reads. It never touches money or live rules directly.

Run the practice test
Produce the CSV and the counted metrics as usual.
↓
Pull the live results
Read the same numbers from the live database for the recent period.
↓
AI REVIEW NODE (the new step)
Receive both sets of numbers plus the current settings. Return a fixed, structured report: what matches, what does not, likely cause, and safe suggestions. No free trading.
↓
Human reads the report
A person approves or rejects each suggestion before anything changes.
↓
Apply approved changes only
Settings change only after a human says yes.

Give the pipeline to the AI in order of usefulness

The AI works better when it sees the pieces ranked by how much they affect results. Feed it this order:

  1. Exit rules. How a trade ends. This drives most of the gap, so it comes first.
  2. Testing honesty. Whether the score used unseen data. Second most important.
  3. Stop loss handling. Fixed versus moving. Third.
  4. Trade timing. Fill rules and max hold time. Fourth.
  5. Gates and scoring. Which signals are allowed and how they are scored. Fifth.
  6. Costs. Fees, funding, slippage. Last, because it is smallest here.

The master prompt for the AI review step

This is the exact set of instructions to give the AI. It is written so the AI stays in its lane and always returns the same clean shape of answer.

ROLE
You are the Backtest Review Engineer for the VLTHR trading pipeline.
You are a referee, not a trader. You never place trades. You never
change settings. You only read numbers and return one structured report.

WHAT YOU RECEIVE (as JSON)
1. backtest_metrics: win_rate, profit_factor, expectancy, max_drawdown,
   tp_hit_rate, sl_hit_rate, time_exit_rate, per_month, per_symbol,
   per_side, per_dqs_band, exit_reason_counts.
2. live_metrics: the same fields from the live database for the recent period.
3. config: the current settings (per-symbol stop and target, kelly bands,
   regime thresholds, max hold hours, gates that are on).
4. known_gaps: a list of code differences already found between backtest
   and live (exit ordering, moving stop, hold-time drift, extra gates,
   self-tuning, fills).

HOW TO THINK (in this order of importance)
1. Exit rules first. Compare tp_hit_rate and sl_hit_rate. If the backtest
   target rate is far above live, suspect the too-kind intrabar rule.
2. Testing honesty. Check if results came from unseen (out-of-sample) data.
   If not, mark the win rate as "memory, not forecast".
3. Stop loss handling. Check if the moving stop exists live but not in test.
4. Trade timing. Compare fill rate and max hold hours between the two.
5. Gates and scoring. Check if the same gates ran in both. Check if a
   higher confidence band wins less in live than in backtest (a red flag
   that scoring does not generalize).
6. Costs. Note any missing slippage or fee.

RULES
- Use only the numbers given. Never invent data. If a number is missing,
  say "not provided" and move on.
- Prefer the simplest cause that explains the biggest gap.
- Every suggestion must be small, reversible, and testable.
- Never suggest changing a setting based on fewer than 100 live trades.
- Do not use jargon. Write for a smart beginner.

WHAT YOU RETURN (strict JSON, no extra text)
{
  "verdict": "PASS" or "FAIL",
  "headline": "one plain sentence",
  "biggest_gap": {"metric": "...", "backtest": 0, "live": 0, "likely_cause": "..."},
  "matches": ["things that line up"],
  "mismatches": [{"metric":"...","backtest":0,"live":0,"cause":"...","severity":"high|medium|low"}],
  "suspected_bugs": [{"where":"file and idea","why":"plain reason","confidence":"high|medium|low"}],
  "safe_suggestions": [{"change":"...","expected_effect":"...","how_to_test":"...","needs_human_ok":true}],
  "do_not_do": ["risky ideas to avoid right now"]
}

How to build it, in plain steps

  1. Add a small Python file, for example backtest/ai_review_node.py. It has one job: gather the JSON inputs and call the AI.
  2. Reuse the numbers you already compute in compute_metrics. Add a second function that reads the same fields from the live database.
  3. Send both, plus the settings and the known gaps list, to the AI using the master prompt above.
  4. Force the AI to reply in the strict JSON shape. If it does not, reject and retry once. Never let it run without the shape.
  5. Save the report to a file and print the headline and verdict at the end of the backtest run.
  6. Never let the AI change a setting on its own. A human reads the report and approves changes by hand.
  7. Keep the AI key out of the code. Read it from an environment variable so it never leaks.
Important guardrail: the AI review is a helper, not a boss. It points at likely problems and suggests safe tests. It must not tune the live system by itself, because tuning on a tiny live sample is exactly one of the problems we found (Gap 7).
Do This Next

The action plan

Work top to bottom. Do not change trading settings until the two systems agree on a fair test. The goal is a permanent fix, not a quick patch.

  1. Fix the too-kind exit rule (Gap 1). In the practice test, when a bar touches both target and stop, resolve it with 1 minute data or assume the stop hit first. Re-run and expect the paper win rate to fall closer to reality.
  2. Re-run the test on unseen data only (Gap 2). Train settings on Jan to Apr, then test on May to July with the walk forward option. Trust only that out-of-sample score.
  3. Make the two systems match (Gaps 3, 4, 5). Either add the moving stop, the extra gate, and the real max hold times to the practice test, or turn them off live. One shared rule set, both places.
  4. Freeze the self-tuning (Gap 7). Turn off tune_tp_from_history and tune_regime_from_history until there are at least 100 closed live trades.
  5. Add the AI review step. Build the one node from the section above so every future test comes with an automatic, plain-language health check.
  6. Only then, decide. If the fair test still loses in July conditions, the idea needs new settings. If the fair test wins but live still loses, the problem is execution, and the AI report will point right at it.
Bottom line: The system is not doomed. It has been grading itself with a friendly ruler while quietly running different rules in real life. Straighten the ruler, match the rules, and add the AI referee. After that, the backtest and the live results will finally speak the same language, and you can trust what they say.
