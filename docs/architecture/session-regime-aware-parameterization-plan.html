1. Codebase Validation of Research Claims

Three claims from the research document were checked against the actual VLTHR codebase. All three are confirmed.

Claim 1: Session is tracked but does not influence trade parameters

VALIDATED. Session is recorded in entry_session on every paper trade and used in DQS context scoring (adaptive_scorer.py :320-331) and calibration lookup (calibration_lookup.py :35-61). But get_symbol_params(symbol) at portfolio_config.py :66-68 only accepts symbol. No session or regime parameter is passed. SL/TP multipliers, RSI thresholds, ADX minimums, and strategy type are identical regardless of session.

Claim 2: Regime scales SL/TP but does not switch strategy

VALIDATED. REGIME_SL_TP_MULTIPLIERS at portfolio_config.py :121-126 scales SL/TP distances by regime. regime_router.py :152-207 does strategy veto: blocks mean_reversion in TRENDING, blocks trend_following in RANGING. But it never switches the strategy. A mean_reversion symbol in a TRENDING regime simply does not trade. It does not adapt to trend_following entries.

Claim 3: Session boundaries are inconsistent across modules

PARTIALLY VALIDATED. The backtest runner defines sessions as: london (07-12), overlap (12-14), ny_open (14-21), ny_late (20-24), asian (00-07) at backtest_runner.py :252-263. The replay runner has a different definition with overlapping time windows at replay_runner.py :47-59 where ny_open (14-21) and overlap (12-20) conflict. ACTIVE_SESSIONS at portfolio_config.py :53 only includes {"london", "ny_open", "ny_late"}, excluding overlap and asian entirely. This means signals during Asian and overlap hours are already gated out before parameter resolution even matters.

Existing Pattern Worth Reusing

Calibration lookup already implements hierarchical fallback. calibration_lookup.py :35-63 has a 6-level fallback: full (symbol+side+strategy+session) to no_session to no_strategy to symbol_only to global to prior. This is exactly the pattern proposed for parameter resolution. The infrastructure for session-aware lookup exists in the calibration layer but not in the parameter layer.

The Sample-Size Rule

The standard practitioner rule (Bailey et al., 2014) requires a minimum of 30 trades per free optimized parameter, per validation cell. With 3 free parameters (SL multiplier, TP multiplier, ADX threshold), that is a minimum of 90 in-sample trades per cell. At 12 trades per cell, the current data is roughly 7.5x under the floor. Parameter estimates below this density are statistically closer to curve-fit noise than to a stable edge.

The Multiple-Testing Tax

Every additional cell fitted is a separate statistical trial. The Deflated Sharpe Ratio (DSR) framework (Bailey and Lopez de Prado, 2014) discounts headline Sharpe by the number of trials, variance across trials, and skew/kurtosis of returns. Practical thresholds:

  • DSR > 0.95: strong evidence of genuine edge after correction
  • DSR 0.80-0.95: probable but borderline, validate further
  • DSR < 0.80: likely noise dressed up as edge

An 80-cell grid search without correction will produce cells that look great from the multiple-testing effect alone. This is the exact mechanism behind "backtest looked amazing, live account bled."

Three Levers That Solve the Break Point

1. Shrink the cell count

Start at session-only: 5 symbols x 4 sessions = 20 cells, ~50 trades/cell. Add regime only where the session-only backtest shows a statistically distinguishable difference in behavior.

2. Hierarchical shrinkage instead of hard per-cell fitting

Fit each cell as a blend between its own data and the parent bucket's data. The sparser the cell, the more it is pulled toward the symbol-level default. This is standard practice in domains with imbalanced bucket sizes (empirical Bayes / partial pooling). It neutralizes the "12 trades is not enough" problem without discarding the session/regime signal.

3. Gate promotion on DSR + CPCV, not on backtest PF alone

A cell only gets its own parameter set live if it beats the symbol-level default with statistical significance after the multiple-testing correction, not just a higher raw profit factor.

Statistical Test for Session/Regime Differentiation

Before writing 80 parameter sets, run a simpler question: for each symbol, is the distribution of trade outcomes (R-multiple, MFE/MAE) in session A statistically different from session B? A two-sample Mann-Whitney U test (non-parametric, since trade P&L is rarely normal) across sessions tells which splits are worth calibrating separately. Collapsing cells that do not show a real difference is itself an overfitting control.

Statistical Gate Infrastructure

Build the overfitting controls as automated gates before any parameter fitting begins. This prevents accidentally promoting an undersampled cell to production.

Deliverables

  • Mann-Whitney U test module: scipy.stats.mannwhitneyu wrapper that takes two arrays of trade R-multiples and returns (U statistic, p-value, effect size). Gate: p < 0.05 required to justify a session split.
  • Sample size validator: Function that takes (cell trade count, number of free parameters) and returns PASS/FAIL against the 30 x N rule.
  • DSR calculator: Function implementing the Deflated Sharpe Ratio formula from Bailey and Lopez de Prado (2014). Inputs: Sharpe ratio, number of trials, variance across trial returns, skew, kurtosis. Output: DSR value and PASS/FAIL against 0.80 threshold.
  • WFE calculator: Function computing Walk-Forward Efficiency = OOS annualized return / IS annualized return. Gate: WFE >= 0.5 required.

Files

  • backtest/stat_gates.py (new): Mann-Whitney, sample-size, DSR, WFE functions
  • backtest/test_stat_gates.py (new): Unit tests with synthetic data
Gate: All 4 statistical functions pass unit tests with known synthetic data. DSR function validated against published example values.

Regime-Specific Strategy Selection

Step 2.1: HMM Regime Detection

Replace the current rule-based regime classification (ADX + efficiency ratio + ATR rank) with a 2-3 state Gaussian HMM over log returns and rolling realized volatility. The current rule-based approach in regime_router.py was explicitly chosen for hardware constraints (4-thread, 7.7GB). The HMM is trained offline and serialized, so the live pipeline only loads a pickle file, same as calibration.json.

  • Library: hmmlearn (GaussianHMM, 2-3 states)
  • Training features: log returns (15m), rolling realized vol (20-bar window)
  • States: trending / ranging (2-state baseline), optional high-vol (3-state)
  • Train per-symbol on 12+ months of historical data
  • Serialize as regime_models/{symbol}_hmm.pkl
  • Live pipeline loads model, calls model.predict() on latest feature window

Step 2.2: Strategy Resolution Function

def get_strategy(symbol: str, session: str, regime: str) -> str:
    """Resolve strategy type from session + regime.
    Falls back to session-level strategy, then symbol-level."""
    sess_params = SESSION_PARAMS.get(symbol, {}).get(session, {})
    base_strategy = sess_params.get("strategy",
                    PER_SYMBOL_PARAMS.get(symbol, {}).get("strategy", "trend_following"))

    # Regime override: switch strategy if regime demands it
    if regime == "TRENDING" and base_strategy == "mean_reversion":
        return "trend_following"
    if regime == "RANGING" and base_strategy == "trend_following":
        return "mean_reversion"

    return base_strategy

Step 2.3: Hierarchical Shrinkage

Do not hard-fit all session x regime cells independently. Each cell's parameters should be a confidence-weighted blend with the session-only parent cell from Phase 1.

def resolve_params(symbol, session, regime, cell_trades, parent_trades):
    cell_params = SESSION_REGIME_PARAMS[symbol][session][regime]
    parent_params = SESSION_PARAMS[symbol][session]

    # Shrinkage weight: more parent data = more pull toward parent
    alpha = cell_trades / (cell_trades + parent_trades)

    return {
        "sl_mult": alpha * cell_params["sl_mult"] + (1 - alpha) * parent_params["sl_mult"],
        "tp_mult": alpha * cell_params["tp_mult"] + (1 - alpha) * parent_params["tp_mult"],
        # ... other params
    }

Step 2.4: Update Entry Filters

Currently v2_filters.py and adaptive_scorer.py use the hardcoded per-symbol strategy. Update them to use the resolved strategy from get_strategy(symbol, session, regime). This means a mean_reversion symbol like XRP can take trend_following entries during a TRENDING regime in the London session.

Phase 2 Gate: Session x regime cell clears both the 30-trades-per-parameter floor AND shows a statistically distinguishable outcome distribution (Mann-Whitney p < 0.05) vs its parent session bucket. Cells that fail either test defer to the session-only params from Phase 1.

Backtest Calibration and Overfitting Audit

Three-Configuration Comparison

Run all three on identical OOS data:

ConfigDescriptionCells
BaselineCurrent fixed global params (per-symbol only)5
Session-awarePhase 1 output: session-specific params per symbol~15-20
Session + regime-awarePhase 2 output: session x regime params with shrinkage~20-40 (after collapsing non-distinguishable cells)

Validation Pipeline

  1. Rolling WFO: 3:1 IS:OOS, minimum 5 cycles (target 8-15). Compute WFE for each config.
  2. CPCV: Run Combinatorial Purged Cross-Validation as the final arbiter. CPCV's purged/embargoed resampling gives a more honest PBO estimate than a single WFO pass.
  3. DSR computation: Compute Deflated Sharpe Ratio for the winning configuration, correcting for the total number of cells/trials searched across Phase 1 and 2.
  4. Promotion decision: Require DSR >= 0.80 before Phase 4. Treat 0.80-0.95 as "proceed to shadow, do not scale size yet."

Fitness Function

Use Calmar ratio (annualized return / max drawdown) on the OOS window, not raw profit factor. This prevents the optimizer from being rewarded for a few large winners that inflate PF without controlling drawdown.

Anti-Overfitting Rules

Do not tune the WFO window sizes, fitness function, or cell boundaries themselves until results look good. That is optimizing the validation harness, which defeats its purpose. Fix these choices in Phase 1 before looking at Phase 2/3 results.
Phase 3 Gate: Session-aware (or session+regime-aware) beats baseline on OOS PF and WR with DSR-adjusted statistical significance (DSR >= 0.80). CPCV PBO < 0.50 (less than 50% probability of overfitting).

Shadow Deployment and Live Rollout

Step 4.1: Orchestrator Integration

  • Resolve params via session + regime at signal time in the orchestrator
  • Store resolved_session, resolved_regime, resolved_strategy on every paper trade for audit
  • These columns extend the existing entry_session, entry_strategy, entry_regime columns. The "resolved" prefix distinguishes the parameter-resolution result from the raw signal classification.

Step 4.2: Shadow Period

  • Run shadow (paper) for a minimum of 2-4 weeks per newly promoted cell, not 2 weeks system-wide
  • Thin cells need their own live-conditions confirmation window since their backtest confidence was lower
  • Monitor per-cell live performance against the backtested OOS expectation (WFE-style comparison, live vs backtest)
  • A large live/backtest divergence on a specific cell is the early warning that its parameters were overfit despite passing the gates

5. Optimization Process and Methods

DecisionChoiceRationale
Search method (Phase 1) Grid search Small parameter space (3 params). Simple and transparent.
Search method (Phase 2) Bayesian optimization (Optuna) Finds comparable optima with far fewer backtest runs. Every additional run is another trial that inflates DSR correction.
WFO window type Rolling, not anchored Rolling prevents parameters from being dragged by market structure that has changed. Anchored suits longer-horizon strategies with stable regimes.
Fitness function Calmar ratio (OOS window) Risk-adjusted. Prevents optimizer from rewarding a few large winners that inflate PF without controlling drawdown.
Regularization Hierarchical shrinkage (mandatory) Primary regularizer against the 80-cell sparsity problem. Not optional once past session-only.
Regime detection Gaussian HMM (hmmlearn) Standard approach in regime-detection literature. Trained offline, loaded as pickle. Avoids brittleness of a single fixed ADX cutoff.
Backtesting Extend existing backtest_runner.py One source of truth. A parallel backtest engine can drift from production logic.

6. Testing Pyramid

Layer 1: Unit Tests

Fallback chain (SESSION_PARAMS[symbol][session] to PER_SYMBOL_PARAMS[symbol] to PARAMS) and get_strategy(symbol, session, regime) resolution. Pure functions. Test every fallback path explicitly, including partially-configured sessions.

Layer 2: Statistical Validation Tests

Automate the Mann-Whitney split test, the 30-trades-per-parameter check, and the DSR calculation as pipeline gates that must pass before a cell's config is allowed to be written to SESSION_PARAMS. This turns overfitting controls into code, not a manual checklist that erodes over time.

Layer 3: Integration / Walk-Forward Tests

Run the full pipeline through rolling WFO on historical data, comparing fixed vs session-aware vs session+regime-aware. Validates that the parameter resolution integrates correctly with all 12 pipeline gates.

Layer 4: Shadow / Paper Trading

Phase 4 with resolved_session / resolved_regime / resolved_strategy audit logging. Any live/backtest divergence is traceable to a specific cell, not just "the system" in aggregate.

Sequencing

Build the statistical gates (Layer 2) before Phase 2, not after. The original plan builds config structure first and validates in Phase 3. Inverting this so the DSR/sample-size/split-test checks exist as automated gates from Phase 1 onward means you cannot accidentally promote an undersampled cell to production.
