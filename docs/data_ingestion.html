Overview

The data ingestion service collects market data from Bybit's V5 API for 6 crypto perpetual symbols across 7 timeframes. It runs as a Docker container with three concurrent processes, writing partitioned Parquet files to a shared volume.

Docker Service
Runs as vlthr-data-ingestion container. Built from ./data-ingestion/Dockerfile. Entrypoint is run_ingestion.sh which launches 3 Python processes. Depends on PostgreSQL health check. Restart policy: unless-stopped.

Architecture

Three concurrent processes run inside a single container, coordinated by run_ingestion.sh. All processes write to the same Parquet store via a shared volume mount.

Process 1: data_scheduler.py

Fetches OHLCV candles (5m, 15m, 30m, 1h, 4h, 1d), funding rates, open interest, orderbook L2 snapshots, and runs the enrichment merger. Uses candle-aligned scheduling with wall-clock offsets.

  • Core module: scheduler_core.py (690 lines) — shared throttle client, incremental fetch logic
  • Ingest core: bybit_ingest_core.py — OHLCV V5 kline fetch, gap detection, backfill
  • Market data: bybit_market_data_core.py — funding, OI, orderbook L2
  • Enrichment: bybit_enrich_core.py — merges OHLCV + OI + funding via merge_asof
Process 2: minute_scheduler.py

Dedicated 1-minute OHLCV fetcher for all 6 symbols. Uses PROXY_URL_2 (secondary proxy) to distribute network load. Fires at :00 + 5s offset each minute.

  • Storage: data/bybit/{SYMBOL}/1m/{YYYY}/{MM}.parquet
  • Rate: 6 requests per minute (0.1 req/s)
  • Proxy: Reads PROXY_URL_2 from env, falls back to PROXY_URL
Process 3: scheduler_monitor.py

Watches scheduler logs, sends Telegram alerts on failures, and produces hourly health reports. Monitors both data_scheduler and minute_scheduler output.

  • Alert channel: Telegram bot
  • Report cadence: Hourly summary
  • Failure detection: Log pattern matching
Process Lifecycle
If any process exits, run_ingestion.sh shuts down all remaining processes via SIGTERM trap. The Docker restart policy (unless-stopped) restarts the container.

Schedule Configuration

All scheduling is candle-aligned. Each data type fires at absolute wall-clock boundaries plus a fixed offset so the fetch happens just after the candle closes.

Startup Behavior

On launch, data_scheduler runs a full sequential pass for all symbols and all data types immediately. No waiting for the first interval boundary. After the startup pass, candle-aligned scheduling takes over.

Sequential Processing
For each interval tick, all 6 symbols are processed one-by-one with a 2-second global throttle between API calls. 6 symbols times approximately 9 requests equals roughly 18 seconds per interval pass. Well inside Bybit's 600 req / 5s limit.

Data Types

OHLCV Candles

Open, High, Low, Close, Volume data from Bybit V5 kline endpoint. Fetched for 7 timeframes (1m, 5m, 15m, 30m, 1h, 4h, 1d). Incremental fetch with gap detection and automatic backfill.

  • Endpoint: https://api.bybit.com/v5/market/kline
  • Category: linear
  • Page size: 1000 candles max
  • Retry: 6 attempts with exponential backoff (base 2.0)
  • Gap detection: Threshold at 1.5x expected interval
Funding Rate

Historical funding rates for each symbol. Fetched hourly with pagination support.

  • Endpoint: /v5/market/funding/history
  • Page limit: 200 records
  • Storage: data/bybit/{SYMBOL}/funding/{YYYY}/{MM}.parquet
Open Interest

Historical open interest data. Fetched hourly.

  • Endpoint: /v5/market/open-interest
  • Page limit: 200 records
  • Storage: data/bybit/{SYMBOL}/oi/{YYYY}/{MM}.parquet
Orderbook L2

Level 2 orderbook snapshots (top 50 bids and asks). Fetched every 5 minutes.

  • Endpoint: /v5/market/orderbook
  • Depth: 50 levels
  • Storage: data/bybit/{SYMBOL}/orderbook/{YYYY}/{MM}/{DD}.parquet
Enriched Parquet

Merges OHLCV + open interest + funding rate into a single file per symbol, timeframe, year, and month. Uses merge_asof with backward direction for temporal alignment. No future leakage.

  • Alignment rule: For each candle timestamp, fetch the most recent OI and funding rate at or before that timestamp
  • Output: data/bybit/{SYMBOL}/enriched/{TF}/{YYYY}/{MM}.parquet
  • Compression: Zstandard
  • Cadence: Every 15 minutes, +120s offset

Write Strategy

Atomic writes via temp file rename. Each partition is written to a .tmp file first, then atomically renamed to the final path. This prevents partial reads by downstream consumers.

  • Compression: Zstandard for enriched, snappy for raw OHLCV
  • Deduplication: On read, timestamps are deduplicated and sorted
  • Validation: Gap detection runs on each fetch cycle

Rate Limiting and Proxy

Global Throttle

All API requests go through a single 2-second cooldown gate in scheduler_core.py. This ensures no burst patterns regardless of how many symbols or data types are being fetched.

  • Cooldown: 2.0 seconds between any two API calls
  • Per interval pass: 6 symbols x ~9 requests = ~18 seconds
  • Bybit limit: 600 requests per 5 seconds (we use 0.5 req/s)

Proxy Support

The ingestion client supports HTTP/HTTPS proxies via environment variables. Useful when Bybit API is not directly accessible from the host network.

  • PROXY_URL: Primary proxy for data_scheduler
  • PROXY_URL_2: Secondary proxy for minute_scheduler (falls back to PROXY_URL)
  • Connection: Connection: close header to prevent connection pool issues in restricted networks
Rate Limit Detection

When Bybit returns retCode 10006 (rate limited), the client reads the X-Bapi-Limit-Reset-Timestamp header to calculate the exact wait time. Falls back to RATE_LIMIT_SLEEP * attempt_number if the header is missing.
