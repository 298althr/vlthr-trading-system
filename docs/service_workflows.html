System Architecture

VLTHR runs 8 Docker services on a single bridge network. All services communicate over internal Docker DNS. Three services are infrastructure (PostgreSQL, Redis, Telegram), three are data and decision (data-ingestion, pipeline, ai-trader-engine), and two are user-facing (backend, frontend).

All Services Run on Docker
Every service in the VLTHR stack runs as a Docker container. There are no bare-metal processes. The entire stack is orchestrated by docker-compose.yml. All services use restart: unless-stopped policy.

End-to-End Data Flow

From Bybit API to user screen, data passes through 6 stages.

STAGE 1: COLLECTION
  Bybit V5 API
    │
    ▼
  data-ingestion container
    ├── data_scheduler.py    → OHLCV 5m-4h, funding, OI, orderbook, enrich
    ├── minute_scheduler.py  → OHLCV 1m
    └── scheduler_monitor.py → Telegram alerts on failures
    │
    ├──→ writes Parquet files to ./data/bybit/{SYMBOL}/{TF}/{YYYY}/{MM}.parquet
    └──→ writes ingestion metadata to PostgreSQL

STAGE 2: SIGNAL GENERATION
  pipeline container (every 5 minutes)
    │
    ├── reads enriched Parquet from ./data/ (read-only)
    ├── reads calibration.json for adaptive scoring weights
    ├── connects to PostgreSQL for signal state, risk ledger, snapshots
    ├── connects to Redis for ephemeral state coordination
    │
    ├── Step 1: Pre-flight checks (safety_layer.py)
    ├── Step 2: Scan 5 symbols, apply V2 filters
    ├── Step 3: Score with adaptive DQS (0-100)
    ├── Step 4: ML prediction in shadow mode (pipeline_brain.py)
    ├── Step 5: State tracking and trajectory (signal_state_manager.py)
    ├── Step 6: Rank and filter (signal_ranker.py)
    ├── Step 7: Crowding detection (Treatment B)
    ├── Step 8: 12-gate portfolio sequence
    ├── Step 9: Upsert approved signals to PostgreSQL
    ├── Step 10: Portfolio snapshot
    ├── Step 11: Telegram alert for EXCELLENT signals
    └── Step 12: Post-flight invariants and trace
    │
    └──→ writes to PostgreSQL: signal_state, signal_state_log, risk_ledger,
         portfolio_snapshot, pipeline_heartbeat, pipeline_trace, predictions,
         model_state, error_log

STAGE 3: API SERVING
  backend container (Express, port 3001)
    │
    ├── reads PostgreSQL for signals, trades, treasury, VTC
    ├── reads Parquet files for candle data, market intel
    ├── connects to Redis for API response caching
    ├── proxies /api/engine/* to ai-trader-engine:8000
    │
    ├── SSE endpoint: /api/signals/stream
    │   └── pushes full state snapshot on every pipeline run
    ├── REST endpoints: /api/paper/trade, /api/vtc/*, /api/overview/*
    └── Engine proxy: /api/engine/pipeline/*, /api/engine/backtest/*, /api/engine/ai/chat

STAGE 4: USER INTERFACE
  frontend container (nginx, port 80)
    │
    ├── serves React SPA static files
    ├── proxies /api/* to backend:3001 (with SSE support)
    │
    ├── useSSE hook: connects to /api/signals/stream
    │   ├── initial event: full state hydration
    │   ├── update event: every 5 min (triggered by pipeline run)
    │   ├── prices event: every 15 seconds
    │   └── intel event: market intel refresh
    ├── Dashboard: signal cards, account summary, live prices
    ├── Signals: watchlist with gate status
    ├── VTC: token price, treasury, audit
    ├── Backtest: D1-D7 pipeline runner, AI chat
    └── Paper: trade management (open, close, history)

STAGE 5: BACKTEST AND AI
  ai-trader-engine container (FastAPI, port 8000)
    │
    ├── reads Parquet from ./data/ (shared volume)
    ├── connects to PostgreSQL for predictions, model state
    │
    ├── /candles, /funding, /open-interest  → market data from Parquet
    ├── /features                           → technical indicator computation
    ├── /pipeline/d1 to /pipeline/full      → D1-D7 backtest stages
    ├── /backtest/start                     → queue backtest
    ├── /probe/symbol                       → regime detection, pattern analysis
    ├── /validate/walkforward               → IS/OOS validation
    ├── /decision/create                    → store AI decisions
    └── /chat                               → NVIDIA AI chat proxy

STAGE 6: NOTIFICATIONS
  telegram container
    │
    ├── reads PostgreSQL for trade state
    ├── sends alerts to Telegram channels:
    │   ├── Trading channel: EXCELLENT signals, trade opens/closes
    │   ├── Status channel: pipeline health, errors
    │   └── Monitor channel: ingestion failures
    └── 3-bot polling architecture

PostgreSQL (TimescaleDB)

Infrastructure Docker Container: vlthr-postgres Image: timescale/timescaledb:latest-pg15 No host port

Role

Primary relational database. Stores all pipeline state, signal tracking, risk ledger, portfolio snapshots, predictions, model state, pipeline traces, and error logs.

Workflow

  • Starts first. Migration script db_migration.py runs on first init via docker-entrypoint-initdb.d
  • Health check: pg_isready -U postgres every 10s. Other services wait for this before starting.
  • Receives writes from: pipeline (every 5 min), data-ingestion (on events), ai-trader-engine (predictions)
  • Receives reads from: backend (API requests), telegram (polling), ai-trader-engine (model state)
  • Data persisted in named volume vlthr_pgdata. Survives container rebuilds.

Redis Cache

Infrastructure Docker Container: vlthr-dashboard-redis Image: redis:7-alpine No host port

Role

In-memory cache. 256 MB, LRU eviction, no persistence. Used by backend for API response caching and by pipeline for ephemeral state coordination.

Workflow

  • Starts independently. No dependencies.
  • No health check (Redis Alpine is reliable, restart policy handles failures).
  • Backend caches API responses to reduce PostgreSQL load on repeated dashboard requests.
  • Pipeline stores transient cross-run state (dedup keys, rate counters).
  • Container restart clears all keys. No data loss risk because nothing in Redis is authoritative.

Relationships

ServiceDirectionPurpose
backendRead/WriteAPI response caching
pipelineRead/WriteEphemeral state, dedup keys

Docker: Yes. Runs as vlthr-dashboard-redis container. No external port. Accessible at vlthr-dashboard-redis:6379 within the Docker network.

Data Ingestion

Data Layer Docker Container: vlthr-data-ingestion Image: python:3.11-slim (build) No host port

Role

Collects market data from Bybit V5 API. 6 symbols, 7 timeframes. Three concurrent processes: data_scheduler (5m-4h OHLCV, funding, OI, orderbook, enrichment), minute_scheduler (1m OHLCV), scheduler_monitor (Telegram alerts).

Workflow

  • Depends on PostgreSQL being healthy (writes ingestion metadata).
  • Fetches OHLCV, funding rates, open interest, orderbook L2 from Bybit V5 API.
  • Enriches OHLCV by merging with OI and funding via merge_asof (no future leakage).
  • Writes Parquet files to ./data/bybit/{SYMBOL}/{TF}/{YYYY}/{MM}.parquet.
  • 2-second global throttle between API calls. 6 retries with exponential backoff.
  • Health check: pgrep -f data_scheduler.py every 60s.

Pipeline Engine

Decision Layer Docker Container: vlthr-pipeline Image: python:3.11-slim (build) Port: 8201:8200

Role

Core decision-making service. Runs a 5-minute loop that scans 5 symbols, scores signals with adaptive DQS, tracks trajectory, ranks, applies 12 portfolio gates, and upserts approved signals to PostgreSQL.

Workflow

  • Depends on PostgreSQL (healthy) and Redis (started).
  • Reads enriched Parquet data from ./data/ (read-only mount).
  • Reads calibration.json for adaptive scoring weights.
  • Runs 12-step iteration: pre-flight, scan, score, predict, state, rank, crowding, gates, upsert, snapshot, alert, trace.
  • Writes to PostgreSQL: signal_state, signal_state_log, risk_ledger, portfolio_snapshot, pipeline_heartbeat, pipeline_trace, predictions, model_state, error_log.
  • Embedded FastAPI health server on port 8200: /health, /last-run, /metrics.
  • Sends Telegram alerts for EXCELLENT signals and trade closures.

Docker: Yes. Runs as vlthr-pipeline container. Built from ./pipeline/Dockerfile. Health port 8200 mapped to host 8201. Command: python -m engine.run_pipeline --loop --interval 300.

Backend (Express API)

API Layer Docker Container: vlthr-dashboard-backend Image: node:22-slim (build) Port: 3003:3001

Role

Express.js API server. Serves SSE signal feed, REST API for paper trading, VTC token management, and proxies requests to the AI Trader Engine. Reads PostgreSQL and Parquet files directly.

Workflow

  • Depends on Redis and PostgreSQL.
  • SSE endpoint /api/signals/stream pushes full state on every pipeline run (5 min) and price updates every 15 seconds.
  • REST endpoints for paper trade management: open, close, list pending/active/closed.
  • VTC engine: token price, score vector, treasury, mint/burn operations.
  • Reads Parquet files directly via parquet-reader.cjs for candle data and market intel.
  • Proxies all /api/engine/* requests to ai-trader-engine:8000.
  • Telegram alert integration for trade events.
  • Health check: GET /api/vtc/treasury every 30s.

Frontend (React SPA)

Presentation Docker Container: vlthr-dashboard-frontend Image: node:22-slim + nginx:alpine Port: 5175:80

Role

React 19 single-page application. User-facing dashboard with real-time SSE signal feed, paper trading, VTC token dashboard, and backtest UI. Served by nginx which proxies API calls to the backend.

Workflow

  • Depends on backend service.
  • Multi-stage build: node:22-slim compiles SPA, nginx:alpine serves static files.
  • nginx proxies /api/* to backend:3001 with SSE support (buffering off, 24h timeout).
  • SPA fallback: all routes serve index.html for client-side routing.
  • useSSE hook manages EventSource connection with auto-reconnect (exponential backoff).
  • 5 pages: Dashboard, Signals, VTC, Backtest, Paper.
  • Auto-execute toggle: auto-opens paper trades for EXCELLENT signals.
  • PWA: service worker for offline shell, push notifications on iOS and Android.

Relationships

ServiceDirectionPurpose
backendRead (HTTP/SSE)All API calls via nginx proxy
ai-trader-engineIndirectVia backend proxy for backtest and AI chat

Docker: Yes. Runs as vlthr-dashboard-frontend container. Built from ./frontend/Dockerfile. Port 80 mapped to host 5175. No direct database or Redis access. All data flows through the backend.

AI Trader Engine (FastAPI)

Analysis Layer Docker Container: ai_trader_engine Image: python:3.11-slim (build) Port: 8002:8000

Role

FastAPI backtest and analysis service. Exposes D1-D7 pipeline stages, strategy management, data exploration, probe endpoints, validation, and NVIDIA AI chat proxy. Reads Parquet data and connects to PostgreSQL for predictions.

Workflow

  • Depends on PostgreSQL being healthy.
  • Reads OHLCV, funding, OI from Parquet store (shared volume).
  • Computes technical indicators on demand via /features.
  • Runs D1-D7 backtest pipeline stages individually or as full pipeline.
  • Manages strategies: create, mutate, list, retrieve.
  • Probe endpoints: regime detection, pattern analysis, parameter suggestions.
  • Validation: walk-forward, Monte Carlo, out-of-sample.
  • NVIDIA AI chat proxy at /chat using NVIDIA_API_KEY.
  • Resource limits: 2 CPUs, 1 GB memory.

Telegram Bot Service

Notification Docker Container: vlthr-telegram Image: python (build) No host port

Role

Telegram bot polling service. Reads trade state from PostgreSQL and sends alerts to Telegram channels. Three bots for different alert channels.

Workflow

  • Depends on PostgreSQL being healthy.
  • Polls PostgreSQL for new trades, trade closures, and pipeline status changes.
  • Sends alerts to three Telegram channels:
    • Trading: EXCELLENT signals, trade opens, trade closures with PnL
    • Status: Pipeline health, errors, circuit breaker triggers
    • Monitor: Data ingestion failures, scheduler issues
  • Health check: os.kill(1, 0) (process alive check) every 60s.

Relationships

ServiceDirectionPurpose
PostgreSQLReadTrade state, pipeline status, signal data
Telegram APIWriteSend alerts to channels

Docker: Yes. Runs as vlthr-telegram container. Built from ./telegram/Dockerfile. No external port. Only talks to PostgreSQL and Telegram API.
