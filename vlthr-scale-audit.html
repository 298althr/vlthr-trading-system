Root Cause Review

Reading the two handoff docs as an RCA analyst, not as the agent that wrote them.

!
Backtest-to-live gap has no assigned cause yet
The system-overview doc says this plainly: "No investigation has been done into why live performance diverges from backtest." That sentence is the whole audit, honestly.
Why 20% live vs 35%+ backtest
  • Low-DQS band still trades. DQS 50-64 signals enter at 0.3-0.7x Kelly. Small size doesn't mean positive edge — if that band is negative-EV after fees, it drags WR down regardless of size.
  • SL may be too tight. 32 SL hits vs 4 TP hits in 54 trades is roughly 8:1. The backtest's own exit table ran closer to 2:1 (971 SL / 533 TP over 1,539 trades). That's a meaningfully different shape, not noise.
  • Sample size cuts both ways. 54 trades is too small to conclude the edge is gone, but it's also too small to conclude it's fine. Neither the "great system" framing nor a full teardown is justified yet — more closed trades are needed before either conclusion holds.
  • No slippage reconciliation exists. Paper fills use the 15m close; real Bybit fills don't. Nobody has compared them side by side.
Compute starvation as a hidden contributor

9 Docker services (Postgres, Redis, ingestion, pipeline, dashboard front/backend, AI engine, Telegram, Bybit WS) are asked to share 3GB of RAM. That's tight enough that docker stats during a normal scan cycle would be worth checking before trusting any other explanation.

Two bugs already logged fit this pattern better than their stated cause: the container zombie issue (processes that won't die cleanly) and the dual execution desync (an order fired on Bybit but the DB link failed during "a brief connectivity window"). Both were filed as network or kernel issues. Both are also textbook symptoms of OOM pressure. Worth ruling in or out with actual memory logs before accepting "network" as final.

Two ledgers, one truth problem

The internal paper simulator shows $9,256 (started $10k). Bybit's own Demo account auto-funds with 50,000 USDT by default — separately from that. If both are logging trades in parallel, they can silently diverge exactly the way the orphaned XRP order already did. Right now there's no single stated source of truth for "how are we actually doing."

Self-certified gates

The Jul 19 handoff concluded "5/6 gates pass, no overfitting, ready for a 1-week demo run" — written by the same process that built the fix being graded. One day later, the Jul 20 doc shows the strategy losing money live. That's not proof the Jul 19 analysis was wrong, but it's a clean argument for never letting the fixing agent be the only one grading its own fix going forward.

Decouple / Recouple Plan

A regime-and-session-aware strategy bank, built so it doesn't repeat the bugs already found twice.

Sequencing matters. A multi-strategy regime bank on top of an unvalidated single strategy multiplies unknowns instead of reducing risk — every new strategy needs its own backtest, its own live-vs-backtest reconciliation, and its own bug class. Stabilize the one strategy currently live first.
Decoupled architecture, four layers

1. Execution Core — ingestion, the Bybit executor, and the risk/sizing gates. Always-on, minimal dependencies, and never duplicated per strategy. The "risk sizing inconsistency" bug (paper using one cap, Bybit using another) happened specifically because sizing logic wasn't centralized — this layer exists so that can't happen again.

2. Strategy modules — one file per strategy, pure functions: bar data + regime tag in, candidate signal out. No strategy module touches sizing, execution, or risk directly.

3. Regime / session router — a cheap, deterministic classifier (see next tab) that tags the current regime and session, and decides which strategy module(s) are "armed" this cycle.

4. Validation harness — walk-forward + shadow-run, run as a separate process from whatever wrote the strategy code. This is the piece that was missing from both handoffs.

How it recouples each scan cycle

Ingestion updates bars → router tags regime + session → router arms the matching strategy module(s) → armed module(s) emit candidate signals → the one shared risk-gate chain (DQS, Kelly, calibration, correlation, daily loss breaker) scores and approves → executor places the order.

The gate chain doesn't change shape as strategies are added — it just sees more candidate signals. This is what keeps sizing and risk single-sourced no matter how many strategies eventually exist.

Why rule-based regime detection, not ML

ADX (trend strength) plus an efficiency ratio (net move / total move) is the standard, well-documented way retail systems classify trending vs. ranging vs. noisy conditions. It's O(1) per bar, needs no training, no GPU, and is trivially walk-forward-testable since the rule never changes. A session tag is even simpler — a lookup table keyed on UTC hour (Asia / London / New York overlap windows).

An HMM or clustering-based regime model is a legitimate upgrade later, but it earns its keep at institutional data volumes and compute budgets — not on a 4-thread, 3GB box where retraining would compete with the executor for the same RAM.

Resources & Validation

What the compute budget can and can't do, and how to prove any of this before real money moves.

The "30% monthly" reality check. Published systematic/CTA fund returns run roughly 8-25% annually; even standout years for top managed-futures funds land around 20%. 30% monthly compounds to something on the order of 2,000%+ a year — not a documented category of sustainable strategy at any public scale. Worth treating as a north star to be skeptical of rather than a spec to build to. A risk-adjusted target (Sharpe or Calmar ratio) is a more honest thing to optimize for than a raw monthly percentage, especially with a strategy that's currently losing money live.
What fits in 3GB / 4 threads

Keep local: the execution core — ingestion, WS client, risk gates, executor. This is the part that must never be starved.

Move off-box: dashboard frontend/backend and the Telegram bot to a free-tier cloud VM; run backtests and any future model training on a separate machine or a notebook environment, and ship only the resulting parameters back down. Phase 5's ML metalabel idea (needs 16GB+) simply isn't a fit for this box at all, on- or off-box training aside.

Set explicit memory ceilings per container so one bloated service can't OOM-kill the executor:

docker run --memory=256m --memory-swap=256m ... # or per-service in docker-compose.yml: # deploy: # resources: # limits: # memory: 256M

Then watch docker stats during a live scan cycle to see which service is actually under pressure before assuming it's network.

Bybit validation mode

Demo Trading is the right environment — api-demo.bybit.com uses the same real-time market data and matching engine as mainnet. Testnet is a separate, less liquid sandbox that's meant for exercising new API features, not for strategy validation. EXECUTION_MODE=demo is already the correct call, no change needed there.

Pick one ledger as truth. Use the Bybit Demo account's own trade history as the source of record, and treat the internal paper simulator as a read-only shadow for comparison — not a second parallel account.

Don't trust WR/PF yet. 54 closed trades isn't enough to distinguish "the edge is broken" from "normal variance." A few hundred closed trades is a more reasonable bar before drawing conclusions either way.

Gate for mainnet: live-demo PF and WR tracking the backtest within a stated tolerance for two consecutive weeks, daily loss breaker never tripped, leverage reconciled — then size small even after that.

What "starting small" looks like here

The framing of "one strategy is wasting compute" and "build a full regime/session bank" treats those as the only two options. There's a cheaper middle step: run Phase A + Phase B only (root-cause fixes + the router as an on/off gate, no second strategy) for the next 2-4 weeks on the current box, and score it against one concrete gate — live PF > 1.2, live WR > 30%, daily-loss breaker never triggered. That's a real answer to "is this a better way to do it," measured instead of guessed at.
